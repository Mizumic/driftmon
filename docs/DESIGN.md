# 设计文档

> 读这份之前请先看 `PREREQUISITES.md`——本文件的每个设计选择都对应那里的一条实测事实。

---

## 1. 要回答的问题

**主问题**：我调用的这个模型后端，**在没人告诉我的情况下**，变了没有？

拆成三个可测量的子问题：

| 子问题 | 可测量的形式 |
| --- | --- |
| Q1 换了服务方没有？ | `x-opencode-endpoint-id` / 上游串 / 响应 id 形态是否变化 |
| Q2 同一个服务方的构建变了没有？ | 在**同一端点内部**，机械行为签名是否漂移 |
| Q3 变化发生在什么时候？ | 签名时间序列上的变点（change point） |

**反问题（明确不做）**：变成了什么模型？几号构建？谁家的？——在没有供应商配合的前提下，
这些问题**原则上不可答**。任何声称能答的实现都是在猜。

## 2. 边界

**能做**：给出「某通道的数值分布发生了统计显著的变化」以及置信度与时间窗。

**不能做**：

* 归因到具体权重版本 / 供应商 / 机房（除非同时观测到端点切换）；
* 在供应商"只换权重、不换 tokenizer、不改任何声明"时给出高置信结论——
  此时最硬的通道（token 计数）失效，只剩统计性较弱的通道；
* 判定"模型变差/变好"——那需要内容评测，不在本项目范围。

**因此产品形态是「观测仪表」，不是「鉴定报告」。**

## 3. 数据流

```
        ┌──────────────────────────────────────────────────────────┐
        │ ① 采样（多会话，固定探针组）                                  │
        │   开 K 个新会话 → 每个发固定请求 → 记录端点溯源 + 通道取值     │
        └───────────────┬──────────────────────────────────────────┘
                        │  append-only
                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │ ② 原始层 data/raw/                                        │
        │   每条样本一行：时间、会话、端点、上游串、id 形态、协议路径、    │
        │   各通道原始输出（用途量、token 计数、logprob 数组、失败位图）  │
        └───────────────┬──────────────────────────────────────────┘
                        │  可重算（纯函数）
                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │ ③ 签名层（派生摘要）                                        │
        │   把一条样本压成数值向量：token 计数向量 / top-k 集合 /        │
        │   失败率 / 延迟分位 / cache 命中率                          │
        └───────────────┬──────────────────────────────────────────┘
                        │  滚动窗口聚合
                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │ ④ 基线层 data/baselines/                                  │
        │   按 (端点, 通道) 维护：中位数、分位数、样本量、观测窗口       │
        └───────────────┬──────────────────────────────────────────┘
                        │  阈值比较 + 变点检测
                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │ ⑤ 判定层 results/                                         │
        │   reports/ 人可读；alerts/ 机器可读；必须可回溯              │
        └──────────────────────────────────────────────────────────┘
```

**关键约束**：②不可再生、③④可重算、⑤必须可回溯（记下用了哪段基线、什么阈值、何时下的结论）。
分成四层的直接原因是端点登记表踩过的坑：第一版把"派生结果"当"原始观测"存，重跑一次就冲掉了历史。

## 4. 采样设计

### 4.1 必须多会话

路由**按会话绑定、到期重选**（实测）。单个会话连跑 89 轮 40 分钟一次没换过端点——
所以**单会话采样只能看到同一个后端**。采样必须：

* 每次开 **K ≥ 8** 个新会话；
* 每个会话发一次固定探针组（不续聊），保证样本独立；
* 从每个样本的响应头记录端点溯源：`endpoint id` / `上游串` / `响应 id 形态`。

### 4.2 固定探针组（内容必须逐次完全一致）

探针组是一组**冻结**的探针定义（放 `probes/`，不允许随机、不允许跟随时间变化），包括：

| 组 | 内容 | 目的 |
| --- | --- | --- |
| T 组 | N 条固定字符串（纯 ASCII / 中文 / 生僻片段 / Unicode 空白 / 特殊 token 字面） | tokenizer 计数差分 |
| L 组 | 1 条固定 prompt，取 M 次样本，`logprobs` + `top_logprobs=5`，`temperature=0` | 分布签名（统计用） |
| G 组 | 14 个已知 glitch token 的「原样复述」任务，R 轮 | 失败率 |
| C 组 | 固定长前缀发两次，读第二次的 `cached_tokens` | 后端是否被换/重启 |
| S 组 | 3 次最小请求，记录 TTFT / 总耗时 | 部署/硬件变化（弱信号） |

**为什么必须冻结**：探针组一旦变化，签名就不可比。任何"顺手改一下探针"都会让历史基线作废。

### 4.3 输出即数据（不做内容分析）

每组的输出只有三类：**用量数字、概率数组、布尔位图**。不保存模型生成的正文。
（**不存"自由生成"的文本**：G 组只存"是否原样复述"的布尔位图，失败时的输出**不落盘**——只记长度。
L 组会存**被采样到的 token 串本身**（它是概率数组的标签，属数值摘要的一部分），这是许可的；
它通常是 1–6 个短 token，不是可用正文。
若将来确需片段取证，必须先在 `docs/DATA-MODEL.md` 里把该例外写进许可清单，而不是就地破例。）

## 5. 判定：先分家，再判定

判定必须先把两类变化拆开，否则端点切换会被误报成"模型悄悄变了"。

```
**分组键是「模型别名」，不是 (别名, 端点)** —— 否则"端点变了没有"这个判断就无从谈起：

对每个「模型别名」分组：

  该别名在窗口内的样本量 < N_min ─────────────▶ insufficient（样本不足，合法结论）

  该别名在窗口内出现过 ≥2 个端点 id ───────────▶ route-change（路由漂移）
  （各端点内部签名分别与各自基线比；跨端点差异一律归到这里，不参与漂移判定）
                                                  │
                                                  │ 窗口内端点唯一且稳定
                                                  ▼
  通道签名与基线比较 ── 全部在噪声内 ──────────▶ stable
                     ── 有通道超阈值 ──────────▶ drift-candidate
                                                  │
                                                  │ 多通道一致 + 多次复现
                                                  ▼
                                              drift-confirmed（附置信度与时间窗）
```

判定结果的取值固定为：`insufficient` / `stable` / `route-change` / `drift-candidate` /
`drift-confirmed`。**不允许出现"其他"**——强制把不确定性表达出来。

## 6. 统计设计（本项目的核心难点）

### 6.1 噪声标定必须先行（Phase 0）

因为 `temperature: 0` 也不可复现（实测），**不能用"两次不一样"当判据**。所以：

1. 先在同一天、**同一端点**上跑 **30 轮巡检（每轮 K≥8 个会话）**，得到每个通道的**自然波动分布**；
2. 用其 p95 / p99 作为阈值下限；
3. 把结果写成 `data/baselines/noise-floor.json`——**这是所有后续判定的分母**。

> **已执行（2026-10-20，官方 `flash 1017`）**：30 轮 / 240 批 / 8640 请求 / 0 错误 → `verdict=calibrated`、
> 五通道可用；实测数字与阈值推导见 `docs/EVIDENCE.md` E10、`docs/PHASE0-PLAN.md §4`。

**噪声底必须按「端点」分别标定，不能全池合并**：因为不同端点的 T 向量本来就不同
（实测 `manhattan-project = 36` vs `orcarouter = 64`），混池会把路由差异当成噪声。

**默认参数（已按 2026-10-20 Phase 0 标定复核）**：

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `K` | 8 | 一轮巡检开多少个新会话（实测每轮 288 请求 / 29.7k token） |
| `M` | 12 | L 通道每个探针组取多少样本 |
| `R` | 3 | G 组跑几轮（失败率取多轮平均） |
| `N_min` | 30 | 判定所需的最小样本数，低于它一律 `insufficient` |
| 「独立通道」 | T 与 G 视为两条独立通道；L 与 S 同源（都反映权重/部署），只算一条 | 防多重比较刷假阳性 |
| 「同向」 | 多条通道的偏移方向一致且都超各自 p95 | 才允许升级为 `drift-confirmed` |
| judge 阈值 | L drop **0.10**、S ratio **2.5**、G z **2**、C drop **0.2** | Phase 0 噪声底 + 滚动回放定值（见 E10） |

**没有这一步，后面所有阈值都是拍脑袋。**

### 6.2 分通道的判据（Phase 0 标定后）

| 通道 | 判据 | 强度 | 2026-10-20 实测（E10） |
| --- | --- | --- | --- |
| T 组 token 计数 | 固定文本的计数向量**逐字节完全相等**才有意义；任何一项不等即疑似配置变化 | **强**（无采样噪声） | 240/240 批恒为 `[18,17,17,39,16]` |
| L 组 logprob | 比 top-k 集合重合度与 logprob 中位数；需要 M ≥ 10 且用分布比较，不用单值 | 中 | top-k Jaccard p05/p50/p95 = 0.786/0.852/1.000（可用）；logprob 退化（IQR=0）→ 只用 top-k |
| G 组 glitch 失败率 | 比多轮失败率（R ≥ 3）的差异，需超过二项分布的置信区间 | 中 | 240 批恒为 3/14=21.4%（CI95 宽 0.028）；噪声为 0，阈值由功效决定 |
| C 组 cache 命中 | 长前缀第二次仍不命中 → 后端被换/重启的强提示 | 中（易被正常过期误伤） | 240 批恒为 0.889；窗口内零波动 |
| S 组 延迟 | 比中位数与 p95 的偏移，需跨天基线 | 弱 | p50/p95 = 128/235ms（p95/p50=1.84，可用）；滚动回放自然最大 2.01× |

### 6.3 多重比较

同时看 5 组通道会让假阳性上升。规则：**单通道超阈值只给 `drift-candidate`；
至少两条独立通道同向超阈值、且连续两次采样复现，才给 `drift-confirmed`。**

## 7. 调度与成本

**成本以 `PREREQUISITES.md §4` 为唯一来源**（实测口径，2026-10-20 Phase 0 校准）：
一次探针组 ≈ 3.7k token；一轮巡检（K=8）≈ 29.7k token。

| 模式 | 频率 | 用途 | 成本（实测折算） |
| --- | --- | --- | --- |
| 基线标定（Phase 0） | 一次性，30 轮 × K=8 | 定噪声底 | **892k token ≈ $0.14** |
| 常规巡检 | 每 6 小时一轮 | 日常漂移 | ≈ $0.58 / 月 |
| 盯梢模式 | 每小时一轮（可临时开启） | 怀疑有灰度时 | ≈ $3.5 / 月 |

详见 `PREREQUISITES.md §4`。**成本不是约束，噪声标定才是。**

## 8. 失败模式（写清楚，避免自欺）

| 失败模式 | 表现 | 缓解 |
| --- | --- | --- |
| 假阳性：端点轮转 | 签名变了，其实是换了服务方 | §5 的 route-change 前置分支；每条样本带端点溯源 |
| 假阳性：噪声 | 单次差异被当成漂移 | Phase 0 噪声底 + 多重比较规则 |
| 假阴性：只换权重 | 所有通道都在噪声内 | **无法根治**；只能靠多通道叠加降低漏检率 |
| 假阴性：供应商改了指纹但你表的近 | 显示原始 md5，命名识别不了 | 保留原始值，不硬猜名字 |
| 数据腐坏：探针组被改 | 历史基线不可比 | 探针组冻结 + 基线带探针组指纹（hash） |

## 9. 与既有资产的关系

| 资产 | 关系 |
| --- | --- |
| `plugins/dsh-system-fingerprint` | **被动层**：拦截真实响应，已提供端点溯源与登记表；driftmon 消费它，不重复实现 |
| `opencode-go/endpoint-registry.json` | **端点台账**：回答"有哪些服务方"；driftmon 回答"服务方变了没有" |
| `SYSTEM_FINGERPRINT_PROBE.md` | 前置知识的原始出处 |
| `.scratch/fp-gateway/*` | 三个原型探针（tokenizer / logprob / glitch），Phase 1 会把它们收进 `src/` |

**分工**：被动（0 成本、持续）看"谁在服务"；主动（低成本、定时）看"变了没有"。

## 10. 开放问题（需要实测才能定，不在本窗口回答）

1. ~~**噪声底到底多大**~~：**已由 2026-10-20 Phase 0 回答**（E10）——L top-k Jaccard p05/p50/p95 =
   0.786/0.852/1.000 且 logprob 退化；G/C 在 240 批内完全恒定；S p95/p50=1.84；五通道均可用。
   未决：L 的小时级非平稳性（0.786↔0.923 模式漂移）是否与负载/时段相关，需跨天复核。
2. ~~**G 组要几轮才稳定**~~：**已回答**——官方 flash 1017 在 240 批里恒为 3/14，集合不变；R=3 足够。
   换端点/权重后是否仍恒定未知。
3. **C 组会不会误伤**：正常 cache 过期与新后端重启如何区分？——需要用「同一前缀连续两次」而非跨时间比；
   Phase 0 窗口内命中率恒 0.889，零误伤，但跨时间行为仍需时间序列。
4. **端点轮转的周期**：目前只观测到"按会话绑定 + 到期重选"，重选周期未知——需要时间序列累积。
5. **跨供应商普适性**：这套通道在 OpenAI / Anthropic 原生端点上的可用性未测（本窗口只测了 DeepSeek 系）。

## 11. 明确不做

* 不抓 prompt / 响应正文；不存凭据；不做内容质量评测。
* 不尝试"逆向"出权重版本号；不基于输出风格做鉴定。
* 不把"统计显著"包装成"确定结论"。
